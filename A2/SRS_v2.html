Executive Summary & Problem Resolution

In Assignment 1 (A1), the AURA Restaurant Application operated strictly as a standalone mobile MVP. All business records—menu catalogs, patron profiles, cart states, table bookings, and kitchen orders—were kept in local mock files and client-side storage (AsyncStorage).

Real-World Problems Observed in A1:

  • Multi-Device Data Desynchronization: When the Manager changed a price or marked a dish sold-out on their phone, diners on other phones still saw old prices and ordered unavailable dishes.
  • Cross-Device Order Invisibility: Orders placed on one device never appeared on another device or after app reinstallation.
  • Table Double-Booking Hazard: Two patrons could book the same table at the same time because each phone checked only local state.

How Assignment 2 (A2) Resolves Every Problem:

  • Single Source of Truth: Central Express server + MongoDB database connects all client devices.
  • Instant Price & Availability Sync: Manager updates via PUT /api/menu/:id persist to MongoDB, immediately reflected on customer devices upon pull-to-refresh.
  • 10-Second Live Order Polling: OrderTrackingScreen polls GET /api/orders/my every 10 seconds, detecting kitchen status changes without restarts.
  • Collision-Proof Bookings: POST /api/reservations queries MongoDB and rejects conflicting bookings with HTTP 409 Conflict.

1. Introduction

1.1. Purpose

This Software Requirements Specification establishes the full functional, database, and architectural requirements for the connected AURA Restaurant Mobile Application. It details the client-server interaction between the React Native frontend, Express.js backend, and MongoDB database.

1.2. Scope

In-Scope (Updated for A2):

  1. Node.js & Express REST API: Modular backend (config/, models/, routes/, controllers/, middleware/) running on port 5000.
  2. MongoDB Database: Production NoSQL database (restaurant_app) with Mongoose schemas for User, MenuItem, Table, Reservation, and Order.
  3. Authentication & JWT Security: Password hashing via bcryptjs, signed 24-hour JSON Web Tokens, and protect / managerOnly middleware.
  4. Dynamic Menu Catalog: Filterable by category and search, with protected manager-only CRUD endpoints.
  5. Server-Validated Orders: Server recomputes total prices from database prices and enforces monotonic order progression (Pending → Preparing → Ready → Served).
  6. Collision-Proof Reservations: Verification of table capacity and rejection of duplicate slot bookings with HTTP 409 Conflict.
  7. 10-Second Polling: Live status synchronization on customer order tracking screen via setInterval.

Out-of-Scope:

  • Real credit card payment processing (Stripe, JazzCash, EasyPaisa).
  • Native OS push notifications (Apple APNs / Google FCM).
  • Real-time GPS courier delivery tracking.

5. Database Design (Replaces Section 5 of A1)

CollectionFields & TypesRelationships & Business Rules
Users
users		 • _id: ObjectId (PK)
• name: String (Required)
• email: String (Required, Unique, Lowercase)
• password: String (Hashed with bcrypt)
• role: Enum (customer, manager)
• phone: String (Optional)
• createdAt, updatedAt: Date 		• Unique index on email.
• Passwords never returned in responses.
• Parent of Orders (1:N) and Reservations (1:N).
MenuItems
menuitems		 • _id: ObjectId (PK)
• name: String (Required)
• description: String (Required)
• price: Number (Required, Min: 0)
• category: Enum (Starters, Mains, Desserts, Drinks)
• image: String (URL)
• isSpecial: Boolean (Default: false)
• isAvailable: Boolean (Default: true)
• createdAt, updatedAt: Date 		• Price cannot be negative (min: 0).
• Referenced by Order.items.menuItem.
• Unavailable items rejected during order placement.
Tables
tables		 • _id: ObjectId (PK)
• tableNumber: String (Required, Unique, e.g. 'A-01')
• name: String (Required)
• seats: Number (Required, Min: 1)
• location: String (Required)
• isWindow: Boolean (Default: false)
• isAvailable: Boolean (Default: true) 		• Unique constraint on tableNumber.
• seats defines maximum allowable guests.
• Referenced by Reservation.table.
Reservations
reservations		 • _id: ObjectId (PK)
• user: ObjectId (FK → User)
• customerName: String (Required)
• phone: String (Required)
• table: ObjectId (FK → Table)
• date: String (YYYY-MM-DD)
• time: String (HH:mm)
• guests: Number (Required, Min: 1)
• status: Enum (Pending, Confirmed, Declined, Cancelled)
• timestamps: true 		• Collision Prevention (Q7): Duplicate bookings for same table, date, and time return HTTP 409 Conflict.
• Table capacity must accommodate guest count.
Orders
orders		 • _id: ObjectId (PK)
• user: ObjectId (FK → User)
• customerName: String (Required)
• items: Subdocuments (menuItem, name, price, quantity, specialInstructions)
• totalAmount: Number (Computed by server)
• orderType: Enum (Dine-in, Takeaway)
• status: Enum (Pending, Preparing, Ready, Served, Cancelled)
• timestamps: true 		• Monotonic State Progression: Pending → Preparing → Ready → Served.
• Cancelled only allowed while Pending.
• Total calculated from DB prices (client totals untrusted).

Shows the end-to-end order placement flow across the three required lifelines: Mobile App, Express Server, and MongoDB.

sequenceDiagram

    actor Customer as Dining Patron
    participant App as Mobile App (React Native)

        Server->>DB: MenuItem.findById(itemId)
        activate DB
        DB-->>Server: Return MenuItem document (price, isAvailable)
        deactivate DB
        Server->>Server: Verify isAvailable === true
        Server->>Server: Line total = DB price * quantity
    end

    Server->>DB: Order.create({ user, items, totalAmount, status: 'Pending' })
    activate DB
    DB-->>Server: Return saved Order document with _id
    deactivate DB
    Server-->>App: HTTP 201 Created (Order JSON)
    deactivate Server
    App->>App: clearCart() & Navigate to OrderTrackingScreen
